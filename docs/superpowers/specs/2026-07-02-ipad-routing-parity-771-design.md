## Ground truth (exploration, 2026-07-02)

- **Datum 1 (inset bleed):** `zapp_ios_push_route_vc` (`routing.m:271`) mints route webviews via the `container_view` mount (`webview.m:1006-1010`) — frame + autoresizingMask only, no safe-area tracking. On iPad-expanded, UIKit keeps the Secondary column full-width and expresses the tiled sidebar (~310pt leading) and iOS-26 inspector column (trailing) as SAFE-AREA INSETS on it — raw-pinned route webviews slide under both. The persistent content webview honors them via the constraint-pair edge model (`sidebar.m:945-1024`: `leadingFull/leadingSafe` + `trailingFull/trailingSafe`, regular→safe / compact→raw). That machinery already exists TWICE (sidebar.m + the no-sidebar mirror `window.m:508-614`, incl. `zapp_ios_pin_content_webview_no_sidebar` `window.m:583-614`); route VCs are the third consumer. The old per-route hook (`ZappRouteVC.viewDidLayoutSubviews` → `zapp_ios_toolbar_inject_webview_safe_area`, `routing.m:68-74`) is a no-op since R3′ env() migration (`toolbar.m:221-230`) — dead weight.
- **Datum 2 (toolbar drop):** root cause (hardcoded identity flags) already fixed at `132ddfc` (routing.m:323-324 live slot-map reads). iPad-expanded is the unverified cell. Remaining structural hazard shared with datum 3.
- **Datum 3 (stale back/fwd):** NOT a missing event — a toolbar-item **generation mismatch**. One `ZappIOSToolbarEntry` per window; each webview's `setItems` rebuilds all `UIBarButtonItem` instances (a new "generation") and stamps `nav.topViewController.navigationItem` (`toolbar.m:467-471`). After a native pop, the revealed content bar holds gen-1 items while `ROUTE_CHANGED(pop)` patches gen-2 (`updateItem` → `entry.itemsById`, attached to the torn-down route VC). Nothing re-applies on pop (`willShowViewController:` owns only bar visibility + metrics). Sibling: route webviews never run `syncToolbar` (`main-pane.ts:87` fixed-route early return) so back/fwd render disabled on pushed pages.
- **New issue A (drop-target global):** every `create_ext` reassigns app-wide `zapp_ios_drop_webview` to the newest webview (`webview.m:1044-1054`); teardown never restores it. After push, system drag-drop targets the route webview; after pop, a torn-down one.
- **New issue B (mid-stack teardown gap):** `zapp_ios_pop_to_content`'s `popToViewController:` (`routing.m:385`) at route depth ≥2 never fires `zapp_route_vc_teardown` for COVERED route VCs (their `viewDidDisappear` ran with `isMovingFromParentViewController=NO`) — "zapp" handlers never removed, zombie bridges. Latent (kitchen-sink pushes depth 1) but real.
- **Foreign WIP (to land in T0):** `toolbar.m` — removes all four `navigationBarHidden` writes; `ZappRouteNavDelegate.willShowViewController:` becomes the exclusive bar-visibility owner (launch primers verified in all three shapes: `sidebar.m:662` didCollapse, `sidebar.m:853` construction, `window.m:824` hidden-Primary — the last written to anticipate exactly this). `webview.m` — `(document.head||document.documentElement)` doc-start fix; `document.head` is null at `AtDocumentStart`, and route webviews rely entirely on this env() script for insets → **load-bearing for datum 1**. `router.nim` — diagnostics only. `multiwindow.ts` — formatting only.
- **No iPhone/iPad fork in routing.m** — single path misbehaving under expanded geometry. One asymmetry: delegate installs at first push (iPad) vs also at didCollapse (iPhone).
- **Prior art:** `.superpowers/sdd/swipe-back-research.md` (3-layer hidden-bar swipe recipe: delegate re-arm with `duringPushAnimation` guard [AHKNavigationController pattern — naive `count>1`/nil-delegate freezes touch], WKWebView pan/scroll `requireGestureRecognizerToFail` arbitration, iOS-26 `interactiveContentPopGestureRecognizer`); N3a spec (per-route webview decisions); rebuild spec `2026-06-29-ios-native-routing-rebuild-design.md` (R2′/R3′ definitions; "close #771").
