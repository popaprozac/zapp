# Nim Editor Config Generation (`zapp/nim.cfg`) — Design

**Status:** DESIGNED — 2026-06-17. CLI-generated, gitignored `zapp/nim.cfg` so
nimsuggest / nimlangserver resolve `import zapp` (and the framework's transitive
imports) in an app's `zapp/app.nim`. Approved shape: generated artifact (not
committed), written at `zapp init` and refreshed every Nim build/dev.

## Problem

An app authored in Nim has a `zapp/app.nim` whose first line is `import zapp`.
The build resolves this because the CLI passes `--path:<framework>/native/nim`
and `--path:<app>/.zapp` to `nim c` (see `cli/src/native.ts` `buildNativeNim`).
But the editor's Nim language server (nimsuggest / nimlangserver) does **not**
see the build command — it reads committed `nim.cfg` / `config.nims` files. So
the whole of `app.nim` shows "cannot open file: zapp" errors even though the app
compiles and runs. This is the reported DX bug.

The kitchen-sink works around it today with a **hand-written, committed**
`kitchen-sink/zapp/nim.cfg` containing monorepo-relative paths
(`--path:"../../native/nim"`) — which only resolve inside this repo, and which a
real installed app could never use. `zapp init` scaffolds `zapp/app.nim` but no
Nim config at all, so a freshly-scaffolded app has broken LSP out of the box.

## Key findings (from exploration)

1. **The Nim framework layer is not self-contained.** `native/nim/zapp.nim`
   `{.compile.}`s sibling sources by relative path: `../platform/darwin/*.m`
   (17 ObjC files), `../worker/engines/zjs.c`, and `-I ../../vendor/zjs/include`.
   `native/nim/` therefore can't be shipped as an isolated package — it's
   inseparable from the whole `native/` tree plus vendored zjs.

2. **The npm package already is the distribution vehicle.** `@zappdev/cli`'s
   `files` include `native/`, and `prepack` copies the monorepo `native/` into
   `cli/native/`. After `bun install`, the framework Nim modules live at
   `node_modules/@zappdev/cli/native/nim/`, and `resolveNativeDir()`
   (`cli/src/paths.ts`) already locates them (monorepo and published layouts).

3. **The build already computes exactly the paths the editor needs.**
   `buildNativeNim` computes `nimFrameworkDir = <nativeDir>/nim` and
   `zappDir = <root>/.zapp` and passes both as `--path`. The fix is to persist
   those same two values into a file the editor reads.

**Conclusion:** this is not a packaging problem; it is a "write the resolution
the build already does into an editor-readable file" problem.

## Decision

Generate `zapp/nim.cfg` from the CLI. Treat it as a derived artifact (gitignored,
regenerated), exactly like the `.zapp/` build output.

### What gets generated

```
# GENERATED by `zapp build`/`zapp init` — do not edit.
# Lets nimsuggest/nimlangserver resolve `import zapp`. Regenerated each build.
# Custom flags? Add zapp/app.nim.cfg or zapp/config.nims (the CLI won't touch those).
--path:"/abs/path/to/node_modules/@zappdev/cli/native/nim"
--path:"../.zapp"
--mm:orc
--threads:on
```

- **Framework path is absolute** — straight from `resolveNativeDir()/nim`. Works
  identically in the monorepo (`<repo>/native/nim`) and an installed app
  (`node_modules/@zappdev/cli/native/nim`); since the file is regenerated and
  gitignored, machine-specificity is fine and it can never mismatch the build.
- **`.zapp` is `../.zapp`** — relative to `zapp/` (where `nim.cfg` lives).
- **`--mm:orc --threads:on`** mirror the build so nimsuggest's semantic checks
  match the real compile. Without `--threads:on`, the `gcsafe`/thread analysis in
  framework modules (e.g. worker/registry) reports phantom errors when the LSP
  walks the `import zapp` graph.
- Rendered by a pure function `renderNimCfg({ frameworkNimDir })` → file text,
  so it is unit-testable without touching disk.

### When it's generated

- **`zapp init`** (Nim scaffold) — alongside the existing `zapp/app.nim` write,
  also write `zapp/nim.cfg` and add `zapp/nim.cfg` to the app's `.gitignore`. The
  editor resolves `import zapp` the moment the scaffolded file is opened.
- **Every Nim build/dev** (`buildNativeNim`, `ZAPP_NATIVE_LANG=nim`) — (re)write
  `zapp/nim.cfg`. Keeps the absolute framework path correct after a fresh
  `clone && install`, a `node_modules` move, or a Zapp version bump.

The **build path does not edit `.gitignore`** — only `init` does (silent edits to
a tracked file are surprising). For a project that pre-dates this feature, the
first build drops an untracked `zapp/nim.cfg`; the user gitignores it once (docs
say so).

### Ownership & escape hatch

The CLI **owns** `zapp/nim.cfg` — the header says "do not edit," and the build
overwrites it. Power users needing custom Nim flags use `zapp/app.nim.cfg` (Nim's
file-specific config) or `zapp/config.nims`; Nim reads all three and the CLI never
touches the latter two. CLI-owned generation and user customization don't collide.

## Components

- `cli/src/build-config.ts` (or a small new sibling) — `renderNimCfg(opts)`: pure
  string renderer. Inputs: absolute framework `native/nim` dir. Output: the file
  text above (`.zapp` path is the fixed `../.zapp`).
- `cli/src/native.ts` `buildNativeNim` — after computing `nimFrameworkDir`, write
  `renderNimCfg(...)` to `<root>/zapp/nim.cfg`.
- `cli/src/init.ts` — in the Nim-scaffold block, write `zapp/nim.cfg` and ensure
  `zapp/nim.cfg` is in the scaffolded/updated `.gitignore`.
- `kitchen-sink/` — `git rm zapp/nim.cfg`; add `zapp/nim.cfg` to
  `kitchen-sink/.gitignore`; let the build regenerate it.
- docs — `docs/api-reference.md` "Authoring an app in Nim": note the editor config
  is generated, gitignored, and refreshed by the build, with the `app.nim.cfg`
  escape hatch.

## Testing

- **bun:test** for `renderNimCfg` — asserts both `--path` lines (framework
  absolute + `../.zapp`), the `--mm:orc` / `--threads:on` fidelity flags, and the
  "do not edit" header.
- **Build assertion** — after a Nim build, `zapp/nim.cfg` exists and contains the
  resolved absolute framework path.
- **Manual LSP smoke (the gate)** — open `kitchen-sink/zapp/app.nim` in the editor
  after a build; `import zapp` resolves with no errors across the file.

## Out of scope

- **No change to the build's own `--path` flags** — already correct; the build
  remains the source of truth, the cfg is editor-only (and Nim harmlessly reads
  both during the build since `app.nim` lives in `zapp/`).

## Future possibility — a real Nim package for Nim-first devs

Publishing Zapp as an installable Nim package (so Nim developers can
`nimble install zapp` / add a nimble dependency and depend on the native
framework directly, outside the npm/bun toolchain) is a worthwhile future
direction — not rejected, just deferred. What it would take, given finding (1):
the package must bundle the **entire** `native/` tree (platform `.m` + worker
engine `.c`) and the vendored zjs (or fetch it), since `zapp.nim` `{.compile.}`s
those siblings — `native/nim/` alone is not shippable. It also introduces a
second package manager alongside npm and a version-sync obligation between the
npm and nimble artifacts. Tractable, but a distinct project; this spec only
solves the editor-resolution DX for the existing npm-distributed framework.
